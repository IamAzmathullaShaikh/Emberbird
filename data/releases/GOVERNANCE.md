# Emberbird Registry Governance

**Scope:** `data/releases/` — the Ember Registry (releases.schema.json, releases.json)
and its evolution. Subordinate to `docs/PHOENIX_CHARTER.md`.

## Ownership

| Component | Owner |
|---|---|
| Registry schema (`releases.schema.json`) | Ember Registry |
| Registry data (`releases.json`) | Ember Registry (generated by `scripts/build_registry.py`) |
| Release contract (`data/contracts/release-contract.md`) | Ember Registry |
| Channel contract (`data/contracts/channel-contract.md`) | Ember Registry |
| Compatibility data | Ember Compatibility |
| Analytics data | Ember Analytics |
| Distribution outputs (winget/choco/scoop) | Ember Distribution |
| Build outputs | Ember Forge |

The registry is **generated, never hand-edited**. To change registry data, change
reality (publish a release) or the generator, then regenerate.

## Schema evolution rules

Every change to `releases.schema.json` requires ALL of:

1. **schema_version bump** — never silently. Compatible additions (new enum
   tokens, new optional fields) bump the minor intent but still bump
   `schema_version` per GOVERNANCE.md discipline.
2. **Migration plan** — a written transformation from the previous
   `migration_version` to the new one, committed with the schema change.
3. **Consumer compatibility review** — every registered consumer (Website,
   Manager, CLI, Winget, Chocolatey, Scoop, Portal) is checked against the
   change before merge.
4. **compatibility_level update** — declare `backward`, `forward`, or
   `breaking` for the release that carries the change. `breaking` requires a
   deprecation window (below).

## Deprecation policy

- Fields are never removed without a deprecation window of at least one
  published registry cycle.
- Deprecated fields are documented in `data/releases/README.md` with their
  replacement.
- Consumers must not read deprecated fields after the window closes.

## Registry Independence & Emergency Recovery

- The registry must remain consumable with **no network access to GitHub**
  (Repository Independence Rule, charter).
- If the registry becomes corrupted or invalid: the **last known-good signed
  registry snapshot** becomes authoritative, consumers continue operating on
  it, and new release entries are blocked until the registry passes
  `python -m platform.release_engine validate` again.
- The reserved `registry_signature` field (schema) will carry snapshot
  authenticity once Emberbird signing ships (P7).

## Validation gates

- `python -m platform.release_engine validate` MUST pass before any registry
  change merges (CI gate via the unit-test suite).
- `tests/test_release_registry.py` pins the contract; failures block merge.
